# 项目理解报告

## 1. 图像生命周期与所有权

图像源通过 `raw.copyTo(buffer_)` 模拟相机复用内部缓冲区。图像尺寸和类型相同时，可以重复使用已分配的内存，减少分配开销。

原来的 `frame.image = buffer_` 是浅拷贝，只复制 cv::Mat 的头部信息，并共享底层像素。引用计数可以防止内存提前释放，但不能防止下一次读取覆盖像素，因此旧帧可能在处理前发生变化。

修改后使用 `buffer_.clone()`，使每帧拥有独立的像素数据。相机后续只覆盖自己的缓冲区，不会影响已经入队的帧。生产者通过 `std::move(frame)` 允许队列接管当前帧的资源。std::move 本身不执行深拷贝，也不能代替 clone；真正的资源转移由移动构造或移动赋值完成。

## 2. 并发处理与恰好一次

保留至少两个 worker 和题目提供的 BlockingQueue。生产者每次成功读取一帧，只入队一次。

push 在互斥锁保护下插入元素，pop 在同一把锁保护下取出并删除队首元素。因此一个队列元素只会交给一个 worker，不会重复处理。唯一的生产者顺序生成帧 ID，每个 ID 对应一个输出文件。

输入耗尽后，生产者调用 close，设置关闭标记并唤醒所有等待者。关闭不会清空队列：只要还有元素，pop 仍然返回帧；队列关闭且为空时，pop 才返回 false。因此正常运行时，已经入队的帧会被全部消费。

等待中的 worker 被唤醒后取剩余帧，或在关闭且为空时退出。正在处理的 worker 先完成当前帧，再尝试下一次 pop。图像处理和保存位于队列锁之外，多个 worker 可以并发处理不同帧。wait 等待所有线程结束，因此正常返回时不会留下尚未处理完成的帧。

## 3. 共享统计数据

生产者更新 produced，所有 worker 更新 processed、saved 和 corrupted，调用线程通过 statistics 读取快照。

原来的递增操作先读取旧值，再写回旧值加一。多个线程可能读取相同旧值，最终写回相同结果，导致计数丢失。无同步地读写共享整数也构成 C++ 数据竞争，行为未定义。

我给 Statistics 添加一把互斥锁，所有更新函数和 snapshot 都使用 std::lock_guard 加锁。递增操作被串行保护，函数结束时自动解锁。用于暴露竞争的人工延迟被移除，所有统计项仍然保留。

snapshot 在一次加锁期间读取全部四个计数，读取过程中不会被其他线程更新，因此快照是安全的。mutex 使用 mutable，使 const 快照函数可以加锁。各项更新仍是独立事件，所以运行中的快照不代表整帧已经完成；所有线程结束后，默认输入的预期结果是 produced、processed、saved 均为 20，corrupted 为 0。

## 4. 线程关闭协议

显式调用 wait 时，先等待生产者结束。生产者在输入耗尽后关闭队列，worker 继续处理剩余元素，队列关闭且为空后退出。调用线程再连接所有 worker，最后 wait 返回。

不显式调用 wait 时，析构函数执行相同的线程回收流程。析构函数体执行期间，图像源、队列、处理器和统计对象仍然存在。等全部线程结束后才销毁成员，因此不会留下悬空访问，也不会因为销毁仍可连接的 std::thread 而触发 std::terminate。

不能在生产者结束前直接关闭队列，否则后续 push 会被拒绝，造成漏帧。也不能只等待 worker 而不关闭队列，否则等待空队列的线程可能永久阻塞。

启动过程中创建线程失败时，关闭队列并回收已经创建的 worker，然后向调用者抛出异常。生产者捕获读取异常并记录错误，随后仍关闭队列；worker 的线程入口也捕获处理或保存异常。后台错误由 wait 在线程全部回收后重新抛出，析构只负责回收，不重新抛出后台错误。异常路径保证安全结束，但输入或保存失败时不能保证所有帧成功输出。

wait 可以重复调用，因为只连接 joinable 的线程；存在后台错误时，重复 wait 会再次报告错误。未启动时 wait 不做任何事。start 只允许进入启动过程一次，重复调用会抛出异常，结束后的对象不能重新启动。生命周期方法要求调用线程顺序执行，不支持并发启动、等待或销毁；输入读取、图像处理和保存操作应能最终结束。
